The Problem

Migrating PVCs in Kubernetes
is a minefield.

Customers stuck on legacy storage want NetApp performance, but moving live data across StorageClasses is harder than it sounds. We learned this the hard way.

⏱️

Hours of downtime

Stopping every workload, manually copying data with rsync, hoping nothing changes mid-flight. A multi-PVC namespace easily turns into a 6-hour maintenance window. Multiply by 40 namespaces and you start praying.

🤖

Operators fight back

PostgreSQL, MongoDB, Dragonfly… they reconcile away your manual changes. Scale a StatefulSet to 0 and the operator scales it back to 3 mid-migration.

↩️

No safety net

If anything fails halfway through, you're staring at a half-migrated namespace at 3am. No rollback, no plan B — just a Slack thread and a coffee.

The INCIBE migration: 40+ namespaces, 500+ PVCs
Spanish customer needs to move every PVC in their cluster from ONTAP FlexVol to ONTAP Qtree — 40+ namespaces, 500+ PVCs. Manual approach for the first few: stop apps, rsync per PVC, swap PV claimRef, restart. It works for one or two namespaces. At scale, it's a nightmare. This is where the toolkit starts.

Any provisioner → any Trident backend
Refactor: source SC and dest SC are now variables, not assumptions. The "FlexVol → Qtree" hardcoding is dead. Add a multi-provisioner lab — local-path, NFS, Longhorn, OpenEBS, Rook/Ceph — so any starting point can be tested end-to-end.

lib-operator-utils.sh
A PostgreSQL Zalando cluster fought back. Built operator detection via ownerReferences and CR matching. Now handles PostgreSQL, MongoDB Community, MariaDB, RabbitMQ, Dragonfly — pause CRs, migrate, restore.
v0.8 · Safety net
Pre-flight audit + rollback scripts
Production incident: PVC mid-migration, namespace stuck. Added pre-migration-audit.sh with BLOCKER/WARNING gates, and per-session rollback.sh generated as each step executes. Any failure can be unwound.
v1.0 · Near-zero cutover
Live sync via native K8s sidecars
K8s 1.29 shipped native sidecars. Inject an rsync container into running pods — no app restart while syncing, continuous background copy. There's still a brief cutover window (apps must restart to bind the new PV), but it shrinks from hours to roughly 30 seconds. Not zero — just very small.
v1.3 · Web UI
FastAPI backend + React frontend
Customers wanted ops engineers without CLI experience to drive migrations. Built a web layer: SSE-streamed progress, operator-warning modals, session management, license activation.
Today · Production toolkit
Commercial-grade, licensed, hardened
JWT licensing tied to cluster fingerprint, HMAC-resistant usage ledger, 152/155 passing tests, three tiers (Base / Plus / Premium). Battle-tested at INCIBE — almost every namespace had at least one operator running, and the GitLab namespace held a single 500 GB volume that had to move cleanly. It did.
How it really works

Warm migration —
the honest version.

There is no live migration between storage provisioners. What there is: a long copy phase while the app keeps writing, an incremental sync that catches deltas, and a brief cutover where pods restart on the new PV. Below is exactly how each piece works and why.

①
Initial copy

Source PVCs are mounted read-write (your app keeps using them). A Kubernetes Job mounts the same PVCs in a copy pod and streams data to the destination:

  • Filesystem PVCs → rsync (preserves perms, ACLs, sparse files, hardlinks).
  • Block PVCs (volumeMode: Block, raw device) → dd from /dev/source to /dev/dest + SHA-256 spot-check.

This phase takes minutes to hours depending on data volume. The app sees zero impact — it does not even know this is happening.

Note on driver vs. mode. What decides the copy strategy is spec.volumeMode, not the underlying provisioner. A SAN/iSCSI/RBD PVC mounted as Filesystem (formatted ext4/xfs by the CSI driver) takes the rsync path — exactly like an NFS PVC. Only raw block devices (volumeMode: Block) take the dd path. Access mode (RWO/RWX) is irrelevant to this choice.

②
Incremental sync — two flavors

While the initial copy ran, the app kept writing. Deltas need to be caught up before cutover. There are two strategies, picked per workload:

  • Sidecar mode (default). A tp-rsync sidecar container is injected into the live pod. It mounts both PVCs and loops rsync every 30s. Used when the workload owner accepts a pod restart to inject the sidecar (most stateful apps).
  • External pod mode. A standalone rsync pod mounts both PVCs in ReadOnlyMany for source (or shares the volume in RWX). Used when the workload cannot be patched: immutable operators, ReadOnlyRootFilesystem, security policies blocking sidecars, or read-mostly workloads where injecting a sidecar would be more disruptive than running externally.

Both modes converge on the same goal: keep the destination PVC within seconds of the source until the operator clicks cutover.

Filesystem only. Incremental sync uses rsync + inotifywait, which require a mounted filesystem to walk. It works for any PVC with volumeMode: Filesystem — NFS, SAN/iSCSI, RBD, local-path, Longhorn, anything — regardless of provisioner or access mode. Raw volumeMode: Block PVCs cannot be continuously synced this way: they take the classic path — full dd copy followed directly by the cutover window, with no rolling delta phase. Live-sync explicitly skips Block PVCs and points the user at migrate-batch instead.

③
What gets scaled — and why

The brief downtime window exists for one reason: a Kubernetes PVC binding cannot change while a pod is using it. So something has to stop. What stops depends on the workload kind:

  • Deployment / ReplicaSet → scaled to replicas: 0, PV swapped, scaled back up. The Deployment is the source of truth; this is safe.
  • StatefulSet → scaled to 0, but we use PV-swap, NOT JSON-patching the VolumeClaimTemplate. STS reconciles new pods that bind the swapped PV by name. Safer than mutating the template.
  • StatefulSet owned by an operator (MongoDB, PostgreSQL Zalando, MariaDB, RabbitMQ, Dragonfly) → the operator is scaled to 0 first, then the STS, then the swap, then the operator is restored. If we scaled the STS without pausing the operator, the operator would fight us and recreate pods on the wrong PVC.

What is never scaled: the Kubernetes API, kubelet, CSI drivers, Trident itself, ONTAP. Only the workload pods using the PVC.

Cases where this does not work cleanly:

  • DaemonSets writing to the PVC (rare, but no clean scale-to-0 — handled manually).
  • Operators not in our supported list — the user is warned at preflight and given a manual pause hook.
  • Workloads with anti-affinity rules that prevent rescheduling on the same node — the cutover window stretches until the scheduler finds a slot.
④
The cutover window

Sequence, end-to-end, typically 30–60 seconds:

  1. Operator (if any) → scale to 0.
  2. Workload → scale to 0. Pods terminate, PVCs released.
  3. Final rsync — flushes the last delta (usually KBs).
  4. PV.claimRef patched: the destination PV now claims the original PVC name.
  5. Original PVC deleted; the rebind happens atomically.
  6. Workload → scaled back up. Pods bind the new PV by name and start.
  7. Operator → restored.

The downtime is real but bounded and measured per migration. If anything fails between step 2 and step 5, rollback.sh generated at planning time restores the original state.
